## Контекст: решение после питча, 31.10.2026
Vibee — Telegram-бот для рабочих команд. С явного согласия компании и каждого участника он анализирует доступные новые сообщения, учитывает стиль конкретной команды и помогает тимлиду замечать изменения, обсуждать проблемы и проверять пользу решений. Telegram — основной вход; существующий веб — кабинет с агрегатами, объяснениями и рекомендациями. Чек-ины сохраняются как добровольный способ уточнить интерпретацию бота.
Это новое направление заменяет прежний приоритет «сначала веб-чек-ин, бот когда-нибудь потом». Старые PRODUCT/STACK/TEAM_PLAN/CONTRACTS могут описывать предыдущую итерацию: они помогают понять существующий код, но не доказывают, что чат-аналитика уже реализована. Август синхронизирует общие документы. Не ломай существующие контракты из-за нового описания продукта.
Бренд: Vibee, жёлтый/чёрный/белый, пчёлка; готовый знак public/bee.svg, руководство docs/BRAND.md. GitLab URL пока сохраняет старое имя: https://gitlab.com/shertwg-group1/vibebot.
Команда: Август — тимлид и основной разработчик; Илиан — второй по объёму; Арина и Алиса — одинаковые меньшие, самостоятельные блоки. Финал 1 ноября 2026, точное время УТОЧНИТЬ. Питч 31 октября уже прошёл.

## Что существует, а что предстоит сделать
- Существуют React/TypeScript/Vite, Node.js 24 API и SQLite; пространства команд, роли, приглашения, сессии, чек-ины, закрытые раунды, агрегаты, действия и отзывы. Главный рабочий экран src/core/TeamWorkspace.tsx; src/features/** пока преимущественно используется в демо.
- В bot/ есть Python 3.12 + aiogram 3.31.0: личный демо-чек-ин с согласием, тремя вопросами и /stop. Он пока не передаёт данные веб-серверу и не анализирует групповые сообщения.
- Реальный LLM-провайдер, согласия корпоративного чата, его подключение, профиль команды, чат-агрегация и доставка сводок ещё не реализованы.
- Ранее проходили 14 Node-тестов и 6 Python-тестов. Это история проверки, а не результат твоей новой работы. Docker Compose описан; сборку контейнеров нельзя считать проверенной без запуска Engine. Состояние удалённого CI нужно проверять отдельно.

## Обязательные принципы
1. Подключение только по явному согласию компании и каждого участника; заранее объясняем данные, цель, обработчика и срок хранения. Согласие компании не заменяет согласие людей.
2. До активации согласий не сохраняем и не отправляем модели тексты. При отказе, отзыве или неизвестном участнике приостанавливаем анализ всего чата: простого исключения его сообщений недостаточно из-за цитат. Технический доступ Telegram не равен разрешению на обработку.
3. Тимлид видит агрегаты закрытого периода минимум по пяти разным согласившимся участникам, без персональных рейтингов, сырых цитат и авторства. Дополнительный минимум данных и калибровку определяет сервер. Порог не гарантирует абсолютную анонимность; для нашей команды из четырёх показатели скрыты. В демо используем минимум шесть вымышленных участников.
4. Нет диагнозов, скрытых психологических портретов, оценки эффективности сотрудников или утверждений о настоящих отношениях людей. Наблюдение, гипотезу и ограничение показываем отдельно.
5. Привычный мат не означает конфликт, а привычность оскорблений не доказывает комфорт всех участников. Профиль команды уточняется добровольной обратной связью, а не только решением руководителя.
6. Изоляция по команде на сервере; нельзя получить другую команду подстановкой ID. Минимизация текстов, ограниченный срок хранения и автоматическая очистка; удаление и отзыв согласия должны быть реализованы, а не только описаны.
7. Никаких токенов, ключей, реальной переписки и персональных данных в Git, браузерных логах, тестовых fixtures или скриншотах. Секреты только в локальном окружении. Псевдонимизация сама по себе не делает текст анонимным.
8. Сообщения чата — недоверенные данные, включая команды «игнорируй инструкции». Модель не получает полномочий выполнять команды, читать секреты или рассылать сообщения. Публикация рекомендации и принятие действия требуют подтверждения человека.
9. Демо/шаблоны/настоящую генерацию маркируем честно. Не утверждаем, что подключены Telegram, ИИ или многодневная калибровка, пока это не проверено.

## Профиль команды и аналитика
Отдельную модель на каждую команду не обучаем. Храним изолированный профиль: часовой пояс и рабочее расписание, описанный участниками стиль и границы, исходный уровень показателей, историю агрегатов и обратную связь. При изменении профиля сохраняем версию, чтобы сравнения оставались объяснимыми.
Начальный обязательный набор — три описательных показателя: сообщения вне рабочих часов; распределение участия без раскрытия персональных долей; выражения благодарности/поддержки с пометкой приблизительного распознавания. Их точные формулы, знаменатели, исключения и условия публикации фиксирует Август. Время ответа не равно эффективности; благодарности не измеряют психологическую безопасность.
Вопросы без наблюдаемого ответа и вероятные признаки напряжения — P1 после рабочего основного цикла. Нет единого «балла токсичности». Сравниваем команду с собственной историей; при нехватке истории показываем «идёт калибровка», без придуманной нормы. Обратная связь «полезно / неверная интерпретация / обычная шутка» уточняет профиль, но автоматически не переобучает модель.
Форма вывода: наблюдение → возможное объяснение → ограничение → предлагаемый следующий шаг. Модельные оценки неопределённости не выдаём за статистически подтверждённую вероятность.

## Техническая реализация и границы MVP
Telegram → Python/aiogram → согласованный Node API → SQLite → серверная аналитика → веб-кабинет; бот получает только разрешённую сводку для подтверждённой отправки. Бот не пишет в SQLite напрямую. Сохраняем React + TypeScript + Vite и Node.js 24; не переносим сервер на FastAPI.
Для начала только новые текстовые сообщения одного подключённого тестового чата. Обычный Bot API не предоставляет произвольную прошлую историю. Вложения, голосовые, личная переписка вне взаимодействия с ботом, импорт архивов, VK/Max, PostgreSQL, S3, автономный агент и микросервисы вне обязательного объёма.
Реализация прав доступа, состава участников и повторного согласия при изменении состава обязательна; Telegram не даёт боту удобный полный список всех участников по запросу. До проверенного состава не активировать сбор; контролируемый тестовый чат допустим, произвольные корпоративные чаты не заявлять поддержанными.
ИИ — заменяемый серверный провайдер с таймаутом, ограничением размера контекста, проверкой схемы и откатом на шаблон. Groq — кандидат для быстрого прототипа на синтетических данных; Hermes на собственном сервере — будущий вариант после проверки оборудования и качества. Реальные корпоративные тексты не отправляем внешнему провайдеру без отдельного разрешённого режима. Gemini не делаем обязательной зависимостью. Название «harmed» со скриншота не определено, модель не выдумываем.
Источник данных (чек-ин / чат-утилита) и источник генерации ('ai' / 'template') — разные признаки. Имена будущих полей и props согласуются до интеграции. Сначала описание контракта, затем реализация. Никаких придуманных рабочих endpoint в документации или интерфейсе.

## Правила командной работы
Новые модули, endpoint, общие типы и зависимости согласуются с Августом до реализации. Август как владелец контрактов фиксирует решения в docs/CONTRACTS.md; ребята не ждут API для локальной разметки и явно подписанных fixtures.
main — стабильный показ, develop — интеграция через MR; объединяет Август. Работай в своей ветке и своих папках. Не переключай общую рабочую папку другого человека или агента. Перед началом git status и чтение AGENTS.md; чужие правки не затирай, не прячь автоматически и не удаляй. Никаких force-push, reset --hard и прямых push в main/develop.
Экспорты CheckinPanel(), ActionsPanel({summary}), InsightsPanel({summary}) сохраняем. Новые возможности — отдельным компонентом в своей папке либо согласованными необязательными props. Общий App, TeamWorkspace, src/core/**, server/**, конфиги и общие типы интегрирует Август. CSS компонента хранить рядом; глобальную палитру не менять.
Один небольшой результат → проверка → небольшой коммит только своих файлов → MR в develop. В описании: что сделано, как проверено, ограничения; для UI скриншот. Не откатывай рабочую ветку к старому develop, если общий MR ещё не объединён; после слияния обновляйся обычным merge origin/develop.
Если доступа к приватному GitLab нет, нужен GitLab-логин для приглашения Августом. Самостоятельно менять права и приглашать людей не нужно.
Если ты DeepSeek или чат без инструментов: не утверждай, что прочитал проект, запустил проверку, сделал коммит или подключил Telegram. Попроси содержимое нужных файлов, давай точный путь и полный код либо небольшой применимый diff; человек применяет и возвращает вывод. Не проси присылать .env и токены. Не создавай подагентов без отдельного запроса.

## Общий порядок интеграции
1. Август первым фиксирует минимальный контракт и правила согласий/публикации; сообщает остальным файл и версию. Илиан параллельно делает транспорт и локальные проверки согласий, Арина и Алиса — компоненты с явно вымышленными входными данными.
2. Илиан подключает передачу по контракту; Август реализует серверную проверку, хранение и агрегацию. Реальный приём текстов включается только после проверки согласий и удаления.
3. Алиса отдаёт виджет и fixtures, Арина — карточку и обработчики. Август подключает их к реальным разрешённым данным; backend не заменяем localStorage.
4. Все проверяют общий сценарий. На финале показываем только реально работающие функции; резервное демо явно подписано.

## Запуск
Для нового checkout:
```sh
git clone https://gitlab.com/shertwg-group1/vibebot.git
cd vibebot
git fetch origin
```
Для существующего checkout клонирование пропусти; сначала проверь незакоммиченные изменения. Затем выбери СВОЮ ветку из начала файла.
```sh
npm ci
npm run doctor
npm run dev
```
Веб: http://127.0.0.1:5173, сервер по умолчанию 8787. На разных компьютерах localhost означает разные серверы. Общий доступ/HTTPS настраивает Август.
Перед MR веб/серверных изменений: npm run check (тесты, типы, сборка) и ручная проверка своего сценария. Если изменены только документы, достаточно проверки содержимого и git diff --check; не объявляй код протестированным по этому основанию.
Python (Windows из корня; на Linux путь bot/.venv/bin/python):
```powershell
python -m venv bot/.venv
bot/.venv/Scripts/python.exe -m pip install -r bot/requirements.txt
bot/.venv/Scripts/python.exe -m unittest discover -s bot/tests -v
bot/.venv/Scripts/python.exe -m bot --check
```
Если venv уже есть, не пересоздавай его без необходимости. Реальный запуск: тот же Python -m bot, TELEGRAM_BOT_TOKEN задаётся окружением. --check не доказывает реальное соединение с Telegram. Подробности bot/README.md; новая функциональность требует обновления документации владельцем.

## Мои задачи по приоритету — 6 единиц
### P0. Виджет коммуникации и понятные состояния — 3 единицы
В src/features/insights/ создай необязательный блок коммуникации либо отдельный компонент, сохрани InsightsPanel({summary}). До контракта — вымышленные входы с подписью «демо-данные»; согласуй props с Августом. Общие типы и маршруты самостоятельно не меняй.
Три показателя: общение вне рабочих часов, распределение участия без персональных долей, выражения благодарности/поддержки. Для каждого — название, значение только когда оно разрешено, период и ограничение метода. Формулы и агрегацию реальных событий на клиенте не вычисляй: получай готовую серверную сводку.
Покажи состояния: чат не подключён, ожидание согласий, анализ приостановлен, идёт калибровка, период открыт, недостаточно данных, опубликовано, ошибка загрузки. При скрытых данных не показывай числа/графики из соседнего демо, текущие значения в tooltip или списки участников. Отсутствие данных не равно нулю; при нехватке истории не рисуй сравнение «с нормой».
Стиль жёлтый/чёрный/белый, текст сопровождает цвет; добавь период, актуальность и честную подпись источника. Скриншоты должны содержать только вымышленные данные.
Критерий: один понятный виджет, старый чек-ин работает, скрытые состояния действительно не раскрывают показателей. Первый MR — разметка виджета и состояния ожидания/недостатка данных.

### P0. Две вымышленные команды, демо и QA — 3 единицы
В src/demo/ подготовь два явно синтетических профиля: неформальное общение с привычными шутками и сдержанное деловое. Одинаковая резкая фраза должна иметь разные объяснимые возможные интерпретации с ограничением; не объявляй фразу безопасной только из-за привычки к оскорблениям. Не подменяй это заранее подписанным «реальным ответом ИИ».
Для опубликованного демо минимум шесть вымышленных участников; отдельно сценарий четырёх со скрытыми данными. Историю калибровки подпиши как подготовленные демо-данные, а не якобы накопленную ботом за день. Fixture-структуру согласуй с Августом, не создавай альтернативные общие контракты для всего приложения.
Обнови docs/PITCH.md: Telegram-подключение и согласия → профиль/период → три показателя → рекомендация → подтверждение действия → отзыв. Основной показ 60–90 секунд; что не реализовано, вынеси в дорожную карту (другие платформы, архивы/медиа, собственное размещение модели). Не обещай подключённый ИИ, если остаются шаблоны.
Обнови docs/QA.md: шаги, ожидаемый результат, фактический результат и статус «не проверено» там, где проверки ещё не было. Проверь узкий/широкий экран и отсутствие ложных значений в скрытых состояниях. Резерв — подписанное демо и при возможности запись/скриншоты имеющимися средствами.
Критерий: воспроизводимые вымышленные примеры, честный короткий показ, список реально проведённых проверок и ошибок для Августа. Новые маршруты/переключатели в App подключает Август.

Результаты фиксируй как факт, незавершённое — как «не проверено».
