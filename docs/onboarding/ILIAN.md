## Контекст
Решение команды от 31.10.2026: продукт «2 в 1» объединяет текущий веб-сервис и корпоративную утилиту — бот/модуль для рабочих чатов Telegram, VK, Max и других платформ. Утилита собирает данные по согласию, а тимлиды работают на веб-платформе с агрегированной статистикой коммуникации, комментариями, рисками/угрозами, способами решения и, если успеем, инструментами налаживания коммуникации. Текущий стек и готовая основа сохраняются; переписывать основу запрещено.
Vibee — веб-приложение: добровольный чек-ин → общий сигнал → подсказка → подтверждённая договорённость → проверка пользы. Слоган: «Почувствовать команду. Сделать следующий шаг».
Три оценки 1–5: ресурс, ясность, поддержка. Статистика только после закрытия раунда и минимум пяти отдельных ответов. Низкая оценка — 1–2; >=40% низких ответов — основание подсказки. При четырёх участниках статистика скрыта, упражнения доступны. Порог — продуктовая гипотеза, не диагностика.
Карточки: цель дня, пересмотр нагрузки, круг помощи, благодарность, переформулирование сообщения по запросу автора.
ИИ пока не подключён: используются честно обозначенные шаблоны. Обучать модель и строить автономного агента для MVP не требуется.

## Принципы 2-в-1
- Утилита подключается только по явному согласию компании и каждого участника чата; участник видит, что именно собирается, и может отказаться.
- Анализ идёт по агрегированным показателям; личные сообщения и авторство не раскрываются руководителю. Порог показа статистики сохраняется (минимум пять участников, закрытый период).
- Выводы не являются диагнозом или оценкой отдельного человека.
- Сырые тексты не хранятся дольше необходимого для анализа; ключи и данные не попадают в Git.
- На питче показываем работающее (веб-чек-ин и подсказки), утилиту обозначаем как «модуль в разработке/дорожная карта», пока она реально не подключена.
УТОЧНИТЬ: состав собираемых данных, агрегированные метрики коммуникации и точный срок хранения сырых текстов.

## Техническое решение
Веб-платформа остаётся на React + TypeScript + Vite, Node.js 24 и SQLite. Telegram-прототип — Python 3.12 + aiogram 3.31.0 в bot/ на feat/ilian-bot. Groq API планируется как серверный провайдер с таймаутом, проверкой ответа, откатом на шаблон и источником 'ai'/'template'; сейчас настоящая генерация ещё не подключена. Локальная модель, PostgreSQL, S3 и микросервисная архитектура не входят в текущую обязательную реализацию. Docker Compose — необязательный способ запуска.
Есть отдельный личный Telegram-демо-чек-ин с согласием, тремя вопросами и /stop. Его передача на сервер и корпоративная активация ещё не реализованы. Не выдавай демо за рабочую корпоративную интеграцию. Подробности: bot/README.md и docs/STACK.md.

Новые модули и endpoint согласуются с Августом до реализации.
main — стабильный показ, develop — интеграция через MR. Работай только в своей ветке/папке. Общие типы, сервер, App, зависимости и конфиги меняет Август.
Сохраняй экспорты CheckinPanel(), ActionsPanel({summary}), InsightsPanel({summary}); новые возможности — через согласованные необязательные props либо отдельный Live-компонент в своей папке.

Маленький законченный результат → проверки → коммит → MR в develop. Август объединяет.
В рабочей ветке уже есть общая основа. Если её MR ещё не слит в develop, не откатывай ветку к develop. Позже обновляй обычным merge origin/develop.
Не используй force-push/reset --hard, не затирай изменения человека, не добавляй .data/.env/ключи и настоящие ответы в Git.
Если нет доступа к приватному проекту, попроси Августа добавить твой GitLab-логин.
Если ты DeepSeek/обычный чат без инструментов: не утверждай, что прочитал файлы, выполнил команды или отправил коммит. Попроси содержимое своего компонента и контрактов; давай по одному файлу точный путь, полный код/diff, команды проверки и ожидаемый результат. Человек применяет и присылает вывод.
Не создавай подагентов без отдельного запроса.

## Мои задачи по порядку
1. P0 — чек-ин (4 единицы). Три вопроса, явный выбор 1–5, понятные крайние значения, клавиатура, подтверждение, успех. Без отправки невыбранных оценок по умолчанию. Первый MR — форма и подписи.
2. P0 — состояния раунда/входа (3 единицы). Подготовь UI открытого/закрытого раунда и уже сохранённого ответа. По согласованию отдельные компоненты входа/создания пространства в своей папке. Не меняй TeamWorkspace.
3. P1 — подключение (3 единицы). Используй api('/checkins',{roundId,scores}). Загрузка, ошибка, повторная попытка, сохранение черновика. STALE_ROUND требует обновления и нового подтверждения. Возвращай новый snapshot родителю согласованным callback. Пока сигнатура не согласована — LiveCheckinPanel рядом, прежний экспорт сохраняется.
4. P2 — прототип утилиты (3–4 единицы). Telegram-бот на Python 3.12 + aiogram 3.31.0 на отдельной ветке feat/ilian-bot в отдельной папке bot/: пока только присылает три вопроса чек-ина и передаёт ответы через согласованный Августом контракт. Анализ переписки на этом этапе не реализуется. Основные пункты — форма чек-ина, состояния и подключение — остаются приоритетнее. Эта ветка и папка относятся только к дополнительному прототипу; основная ветка и пути выше сохраняются.
УТОЧНИТЬ: согласованный Августом контракт передачи ответов бота. Нагрузка обновлена: 10 исходных + 3–4 дополнительных = 13–14 единиц.
Критерий: закрытый раунд не принимает ввод; повторный чек-ин заменяет старый; ошибка не уничтожает черновик; доступно с клавиатуры и на узком экране.
