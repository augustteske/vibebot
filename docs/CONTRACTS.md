# Контракты v1 — командный сервер и демо
Обновлено 3 ноября 2026 года. Репозиторий: https://github.com/augustteske/vibebot. Существующий API чек-инов ниже сохраняется. Маршруты Telegram v1 реализованы только в закрытом синтетическом контуре и выключены в обычном запуске.

## Стек и запуск
React + TypeScript + Vite, Node.js 24, встроенный node:sqlite. npm run dev запускает интерфейс (5173) и API (8787); /api проксируется Vite на сервер. npm run build и npm start раздают готовый dist вместе с API с порта 8787. Локальное SQLite-хранилище и серверный ключ находятся в игнорируемой .data. Настройки загружаются из необязательного .env; см. .env.example.

## Существующие компоненты команды
- src/core/model.ts: Scores { energy, clarity, support }, каждое значение — целое 1..5.
- Summary: { status: 'open' } | { status: 'insufficient' } | { status: 'published', means: Scores, needs: Array<keyof Scores> }.
- CheckinPanel() — локальный демо-компонент чек-ина.
- InsightsPanel({ summary }) — демо-компонент показателей.
- ActionsPanel({ summary }) — демо-компонент рекомендаций.
Имена экспортов и эти props сохранены. Модули ребят не менялись. Командный режим временно собран в src/core/TeamWorkspace.tsx — это работающий интеграционный пример, из которого можно постепенно вынести готовые компоненты по согласованию.

## Общий клиент
src/core/client.ts: api<T>(path, input?). Без input — GET, с input — POST JSON с X-Vibee: 1. Cookies передаются same-origin. Таймаут 10 секунд; ApiError содержит status, code, message. Значения key/token никогда не писать в логи или коммиты.

src/core/contracts.ts: SessionSnapshot, Suggestion, TeamAction, FeedbackSummary, CheckinInput.
SessionSnapshot содержит только своё имя/роль, пространство, текущий round с допустимым Summary и собственным mySubmitted, доступные шаблонные предложения и общие договорённости. Списка голосовавших, числа текущих ответов и сырых ответов в нём нет.

## Реализованный API
Все пути начинаются с /api. Для изменяющих запросов нужен JSON и X-Vibee: 1 (старый X-Vibebot: 1 также принимается). Браузерный Origin проверяется. Ответы не кешируются.

| Метод и путь | Тело | Доступ / результат |
|---|---|---|
| GET /health | — | {ok:true} |
| POST /workspaces | {name, displayName} | Новое пространство и организатор; устанавливает cookie, возвращает SessionSnapshot |
| POST /join | {token, displayName} | Одноразовое приглашение; создаёт участника и сессию |
| POST /restore | {key} | Возвращает того же участника с теми же правами |
| GET /session | — | SessionSnapshot своей команды либо 401 |
| GET /summary | — | Summary текущего раунда своей команды либо 401 |
| POST /logout | {} | Отзывает текущую сессию |
| POST /recovery-key | {} | Свой личный код входа на 30 дней; новый заменяет старый |
| POST /invitations | {} | Только организатор: {token, expiresAt}; одно использование, 24 часа |
| POST /checkins | {roundId, scores} | Сохранение/замена своего ответа в текущем открытом раунде |
| POST /rounds/close | {roundId} | Организатор: замораживает допустимый агрегат, удаляет отдельные ответы |
| POST /rounds/open | {} | Организатор: следующий раунд, если текущий закрыт |
| POST /actions | {roundId, suggestionId, goal} | Подтверждённый общий шаг; goal 1..500 символов |
| POST /actions/:id/feedback | {helpful:boolean} | Сохранение/замена своего отзыва |
| POST /actions/:id/close-feedback | {} | Организатор: замораживает допустимый агрегат и удаляет индивидуальные отзывы |

Изменения чек-инов, раундов, договорённостей и отзывов возвращают актуальный SessionSnapshot. Для приглашения и кода входа возвращается отдельный объект. Ошибки: {error:{code,message}} с HTTP 400/401/403/404/409/413/415/500. Конфликт roundId возвращает 409 STALE_ROUND, закрытый раунд — 409 ROUND_CLOSED.

## Приватность и ограничения
- Участник определяется сессией приглашения; при восстановлении личным кодом новый голос не создаётся.
- Организатор выдаёт отдельное приглашение человеку; реальная личность не удостоверяется.
- В таблице ответов используются HMAC-псевдонимы, отдельные для каждого раунда/действия. Прямого memberId в строке ответа нет; абсолютная анонимность от владельца сервера не обещается.
- После закрытия раунда/отзывов отдельные ответы удаляются, хранится только допустимый замороженный результат.
- Публикация после закрытия и минимум пяти отдельных ответов. Открытый и малый раунд не содержат средних значений и нужд.
- Низкая оценка — 1–2; доля >=40% запускает соответствующую подсказку. Это проверяемая стартовая гипотеза.
- Ключи сессий, приглашений и восстановления хранятся хешированными. Cookies HttpOnly/SameSite=Strict; для HTTPS выставить COOKIE_SECURE=true.
- Максимум два принятых шага за скользящие 24 часа, один вид шага за раунд. Для закрытого раунда выбираются максимум две нужды; при отсутствии опубликованных нужд доступно добровольное признание вклада.
- Сбор закрывает организатор; автоматического календарного расписания пока нет.
- Внешнее развёртывание, корпоративная авторизация, резервное восстановление и несколько экземпляров сервера пока не реализованы.

## ИИ
Серверный провайдер чат-рекомендации принимает только опубликованные агрегаты; его контракт не меняется. Отдельный экспериментальный модуль `server/text-analysis.mjs` запускается вручную командой `npm run analyze:synthetic` и использует только фиксированные синтетические примеры. Он не связан с Telegram, метриками, базой данных или API приложения. Для внешнего вызова настройте `TEXT_ANALYSIS_PROVIDER=openai`, `TEXT_ANALYSIS_MODEL=gpt-5.4-mini` и серверный `OPENAI_API_KEY` в `.env`; без ключа команда возвращает `unavailable`, не подставляя шаблон. Исходные примеры и ответы не записываются и не логируются. Этот демо-режим не разрешает обработку реальных сообщений.

Для первого опыта выбран OpenAI `gpt-5.4-mini`: это быстрый mini-вариант для ограниченных задач; официально заявлены текстовый ввод, Chat Completions и строгие structured outputs. По опубликованным тарифам он дешевле полноразмерного GPT-5.4 ($0.75/$4.50 против $2.50/$15 за 1 млн входных/выходных токенов; данные на 3 ноября 2026 года). Документация не даёт отдельной гарантии качества русского языка, поэтому русские ответы требуют собственной оценки. API-данные по умолчанию не используются для обучения, но содержимое запросов может храниться в abuse-monitoring логах до 30 дней; это не нулевая ретенция. См. [модель и цены](https://developers.openai.com/api/docs/models/gpt-5.4-mini), [structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs) и [обработку данных](https://developers.openai.com/api/docs/guides/your-data).

Свободная автономия, психологические выводы и обучение с нуля в критический путь не входят. Для подключения анализа реальных сообщений нужны отдельные согласия, правила хранения/отзыва, оценка обработки данных провайдером и отдельное изменение контрактов.

## Telegram v1 — контракт реализации P0

Статус: серверные операции привязки, согласий, приёма текста, периодов, рекомендаций и обратной связи реализованы для закрытого синтетического контура; обычный сервер их не включает. Локально его можно включить только при `NODE_ENV=development`, `VIBEE_TELEGRAM_SYNTHETIC=true` и настроенном `VIBEE_TELEGRAM_BOOTSTRAP_CREDENTIAL`; вне development сервер завершится с ошибкой. Python HTTP transport и локальный синтетический API совместно проверены, но цепочка от настоящего Telegram update и подключение реального чата не проверены. Это не разрешение на сбор реальных текстов.

### Идентичность и границы

workspaceId — существующая команда; bindingId — серверная привязка одного контролируемого группового чата к ней. Один chatId может иметь только одну действующую привязку. Все Telegram ID передаются десятичными строками, время — ISO 8601 UTC. Период чат-аналитики имеет свой periodId, не roundId чек-ина. Новый участник веба при связывании не создаётся.

Режим MVP — синтетический закрытый тестовый чат с проверенным составом. Организатор подтверждает полномочия представителя компании отдельно от своей веб-роли. Владелец тестового чата вручную сверяет полный состав в Telegram; сервер требует связать каждого человека с существующим участником команды. Обычный Bot API не доказывает полноту списка. Если состав нельзя проверить, активация запрещена. Служебный бот исключён; другие боты, анонимные администраторы и sender_chat не поддержаны и вызывают паузу.

Связь личности: вошедший веб-участник получает одноразовый linkToken на 10 минут (в БД только хеш); предъявляет его в личке боту. Сервер связывает подтверждённый from_user.id с этим memberId сначала на уровне команды, а после привязки чата — с bindingId. Один Telegram ID и один memberId на команду/привязку; конфликт отклоняется. Одноразовый bindingToken организатора связывает группу только после проверки ботом Telegram-прав инициатора и совпадения его связанного ID с веб-организатором. Токены не логируются.

### Авторизация

Браузер использует существующую сессию, Origin и X-Vibee. Начальный bearer бота задан сервером и разрешает только POST bot/v1/links и POST bot/v1/bindings; он не даёт доступа к существующей привязке, согласиям, статусу, сводкам или событиям. При создании привязки сервер выдаёт отдельный scoped credential и хранит только его хеш с workspace/binding. Bootstrap credential не заменяет одноразовый bindingToken и проверку личности организатора. Нужны отзыв и ротация. За пределами loopback обязателен HTTPS.

Сервер выводит команду из авторизации; workspaceId из тела не принимается. Для недоступной привязки — 404. Решение участника принимает только его связанный Telegram ID через личный диалог. Право организатора не позволяет давать согласия за людей. Транспорт считается доверенным в проверке Telegram updates; это не защита от компрометации самого бота.

### Конечный автомат согласий

Состояние хранится сервером: phase, revision, policyVersion, rosterVersion, rosterVerified, companyAccepted, roster и решения участников. roster/decisions — внутренние поля, никогда не публичный статус. Начало disconnected, revision=0. Каждое принятое новое событие увеличивает revision на 1; изменение состава также увеличивает rosterVersion.

| Событие | Условие | Результат |
| --- | --- | --- |
| bind | disconnected; проверены полномочия и привязка | awaiting_consents |
| roster | проверенный непустой состав без дублей | paused; все личные согласия сброшены |
| company(true) | подтверждены полномочия представителя | согласие компании; без автоактивации |
| decision(accepted) | свой связанный участник текущего состава | согласие; без автоактивации |
| decision(declined/withdrawn), company(false) | авторизованный субъект | paused немедленно |
| unknown_member | неизвестный отправитель/неподдержанная личность | paused; состав непроверен, личные согласия сброшены |
| policy | новая версия условий | paused; согласия компании и людей сброшены |
| pause | ручная остановка, простой, потеря событий, миграция chatId | paused |
| resume | состав проверен, компания и ВСЕ участники согласны с текущей версией | active по явному подтверждению организатора |
| disconnect | авторизованный организатор | disconnected; связи и согласия очищены |

Первая установка состава тоже приводит в paused: это сознательная остановка до явного resume. Порог пяти нужен для публикации, а не для согласий: согласиться должны все участники независимо от размера группы.

Команды изменения несут expectedRevision. Старая кнопка/гонка → 409 STALE_REVISION, получить статус и показать новый запрос подтверждения; автоматически повторять принятие согласия на новой версии нельзя. Отзыв при конфликте повторяется с актуальной revision до подтверждения; бот сразу прекращает пересылку и не заявляет об успешном серверном отзыве до ACK. Дубликат того же requestId возвращает прежний результат без нового перехода.

Перед приёмом текста, запуском модели и публикацией сервер повторно проверяет active и revision. Смена revision инвалидирует незавершённые задания: результат старого задания отбрасывается. Проверка и запись/публикация — одна транзакция. Чистая функция transitionConsent предполагает уже выполненные проверки полномочий и входной JSON-схемы; сама их не заменяет.

policy обновляется серверным администратором при изменении условий, не ботом. Подтверждения инициатора/получателя перепроверяются сервером по связанному членству и роли. Сводка не отправляется в группу; recipientId должен совпадать с личным получателем запроса. Отправка заново проверяет актуальность revision; внешнюю доставку нельзя сделать атомарной с отзывом, уже доставленное сообщение не обещаем удалить.

При потере ответа POST bot/v1/bindings бот повторяет тот же requestId и тело в течение 24 часов: сервер возвращает тот же scoped credential без второй привязки. Credential выводится из постоянного серверного секрета и параметров привязки через HMAC; открытый credential и bindingToken в SQLite не сохраняются. Изменённое тело с тем же requestId → 409 EVENT_CONFLICT. Сервер сверяет связанную личность и роль веб-организатора, срок/одноразовость токена и уникальность chatId. Доверенный бот отдельно устанавливает по Telegram update подлинные chatId и from_user.id инициатора и проверяет его права в группе; переданные поля сами по себе этого не доказывают. Реальный маршрут остаётся выключенным до такой проверки в боте.

### Схема события TelegramTextEvent, повторы и сбои (раздел B)

Синтетический пример POST events:

```json
{"eventId":"9b747012-4ed2-42eb-bd29-195713790690","expectedRevision":9,"chatId":"-1000000000001","messageId":"42","senderId":"100000001","sentAt":"2026-10-31T08:00:00.000Z","text":"Спасибо за помощь с тестовым примером"}
```

Точная схема тела (неизвестные поля запрещены):

```ts
type TelegramTextEvent = {
  eventId: string          // UUID; сохраняется неизменным при повторе доставки
  expectedRevision: number // безопасное целое >= 0
  chatId: string           // отрицательный Telegram ID, десятичная строка
  messageId: string        // положительный Telegram ID, десятичная строка
  senderId: string         // положительный Telegram ID, десятичная строка
  sentAt: string           // UTC ISO 8601 строго с миллисекундами и суффиксом Z
  text: string             // непустой текст, максимум 4096 Unicode code points
}
```

Все семь полей обязательны; тело JSON — не более 32 KiB. Ответ HTTP 200: `{eventId, result:'accepted'|'duplicate'|'paused', revision}`. `paused` означает, что отправитель не сопоставлен с участником проверенного состава: сервер приостанавливает привязку, увеличивает revision, очищает сырые сообщения и производные данные и не принимает этот текст. При обычном `accepted` новое событие учитывается ровно один раз; `duplicate` не меняет счётчики. Конфликт повторного eventId/messageId с иным содержимым — 409 EVENT_CONFLICT.

Только новый непустой текст, максимум 4096 Unicode code points; возраст <=60 секунд, будущее <=30 секунд по серверным часам. senderId принадлежит проверенному составу; неизвестный отправитель останавливает чат без сохранения текста. Привязка chatId проверяется независимо от credential. События до активации/во время паузы отбрасываются без диска, модели и логирования тела.

eventId стабилен при повторе. Два уникальных ключа: (bindingId,eventId) и (bindingId,chatId,messageId). Дубликат с тем же содержимым не меняет агрегат; конфликт содержимого → 409 EVENT_CONFLICT. Сравнение по keyed digest, не хранить дополнительную копию текста. Сначала авторизация/согласия, затем проверка дубля. Метаданные дедупликации живут 24 часа; окно допустимой доставки 60 секунд предотвращает поздний повтор после очистки.

MVP не применяет edited_message: правка известного сообщения вызывает pause с reason=message_edit, очистку сырых текстов и открытого периода. Обработчик `edited_message` в `bot/__main__.py` есть, но работа с настоящими Telegram updates не проверена. Миграция chatId требует новой привязки и подтверждения состава; автоматически переписывать ID нельзя. Нет импорта истории и гарантированного зеркалирования Telegram-удалений.

Бот: таймаут 5 секунд, максимум 3 попытки с тем же eventId (задержки 1 и 2 секунды) только при сетевой ошибке/429/5xx и в пределах 60 секунд. Очереди на диске нет. При неустранённой ошибке локальная пауза немедленно; после восстановления сначала server pause с transport_gap, затем ручной resume. Неполный период не публикуется.

Ошибки {error:{code,message}} без отражения текста/токенов: 400 INVALID_INPUT, 401 BOT_AUTH_REQUIRED, 403 FORBIDDEN, 404 NOT_FOUND, 409 STALE_REVISION / CONSENT_REQUIRED / EVENT_CONFLICT / STALE_PERIOD, 413 TOO_LARGE, 415 JSON_REQUIRED, 429 RATE_LIMITED, 503 UNAVAILABLE. Retry-After для 429. Повтор requestId с другим телом → EVENT_CONFLICT; дедупликация и мутация атомарны.

### Расширение Telegram v1: серверный синтетический приём медиа; остальное не реализовано

Серверный `media-observations` реализован только в закрытом синтетическом контуре. Бот по-прежнему передаёт только `F.text`, `bot/intake.py` формирует только семипольный `TelegramTextEvent`. Обычный Telegram-режим и медиа-анализ остаются выключены. Сервер принимает медиа только при `policyVersion='synthetic-media-v1'`, активной привязке и полном согласии компании и **каждого** участника на эту версию; прежнее `synthetic-v1` не подходит. Переход между версиями условий требует отдельного сброса и повторного сбора согласий, автоматического обновления нет. Telegram update может содержать медиа-поля уже при доставке боту; до `active` бот не должен их извлекать в payload, сохранять, логировать, запрашивать `getFile` или скачивать байты. Сервер независимо проверяет scoped credential, chatId, revision, полный состав и срок свидетельства согласия **до** записи. Неизвестный отправитель останавливает весь чат по существующему правилу.

| Вид | Метаданные после полного согласия | Текст после полного согласия | Содержимое файла |
| --- | --- | --- | --- |
| Голосовое сообщение | Только `messageId`, `senderId`, `sentAt`, тип, заявленные `mimeType`, `fileSize`, `durationSeconds`; без `fileId`, `fileUniqueId`, имени и пути | Подписи нет; будущая расшифровка — отдельный производный текст, не исходная подпись | В первом срезе не получать и не хранить; будущий отдельный обработчик, не JSON `/events` |
| Видеокружок | Те же поля; `durationSeconds`, без кадров, миниатюр и координат | Подписи нет; извлечение речи в будущем отдельно | В первом срезе не получать и не хранить; изображения/кадры не анализировать |
| Файл (`document`, включая аудио/видео как документ) | Те же поля, но `durationSeconds` отсутствует; не передавать `fileName`, `fileId`, `fileUniqueId`, MIME-параметры и миниатюры | Только Telegram `caption`, если она есть; содержимое документа не превращать в текст автоматически | В первом срезе не получать и не хранить; архивы и вложенные файлы не раскрывать |
| Подпись к медиа | Тип носителя, общие поля сообщения и ограниченные метаданные носителя | `caption` — самостоятельный текст, максимум 1024 Unicode code points; не подменять ею `text` существующего события | Подпись не даёт разрешения скачивать файл |
| Описание чата | `chatId`, время наблюдения, revision; без списка участников и истории изменений | Полное новое описание, максимум 255 Unicode code points; это текст группы, а не сообщение участника | Файла нет |

**Первый маленький срез:** в закрытом синтетическом контуре принять только `TelegramMediaObservation` для `voice`, `video_note` и `document` с необязательной подписью; не скачивать файл и не расшифровывать речь. Событие служит проверяемым учётом разрешённого формата и кратковременной подписи, но **не входит** в `M`, `O`, `R`, `K` и калибровку существующих трёх метрик. Подпись не становится вторым сообщением. Показатели и карточки из нового типа не публикуются. Описание чата — следующий отдельный срез, после проверки источника Telegram update и согласий; не посылать его как сообщение и не включать в метрики. Фото, обычное видео, стикеры, альбомы, пересланные сообщения, анонимные отправители и другие типы остаются вне среза.

Реализован `POST /api/bot/v1/bindings/:id/media-observations`; `POST /api/bot/v1/bindings/:id/chat-description` остаётся планом. Тела — JSON не более 32 KiB, неизвестные поля запрещены; идентификаторы и время имеют ограничения `TelegramTextEvent`. `mimeType` — строка из явного allowlist ниже, не доверенный способ определить содержимое. `fileSize` и `durationSeconds` — целые безопасные числа в указанных пределах, не основание для загрузки файла. Подпись может отсутствовать, но пустая строка запрещена. У `voice` и `video_note` подпись запрещена. Поля Telegram `fileId`, `fileUniqueId`, URL, base64 и байты файла запрещены в обоих JSON-телах.

```ts
type TelegramMediaObservation = {
  eventId: string          // UUID, стабилен при повторе
  expectedRevision: number // целое >= 0
  chatId: string           // отрицательный Telegram ID
  messageId: string        // положительный Telegram ID
  senderId: string         // положительный Telegram ID
  sentAt: string           // UTC ISO 8601 с миллисекундами и Z
  media: (
    | { kind: 'voice'; mimeType: 'audio/ogg'; fileSize: number; durationSeconds: number }
    | { kind: 'video_note'; mimeType: 'video/mp4'; fileSize: number; durationSeconds: number }
    | { kind: 'document'; mimeType: 'application/pdf' | 'text/plain'; fileSize: number; caption?: string }
  )
}

type TelegramChatDescription = {
  eventId: string          // UUID, стабилен при повторе
  expectedRevision: number
  chatId: string
  observedAt: string       // UTC ISO 8601 с миллисекундами и Z
  description: string      // непустая строка, максимум 255 Unicode code points
}
```

Для `voice`: `fileSize` 1..10 MiB и `durationSeconds` 1..120; для `video_note`: 1..20 MiB и 1..60; для `document`: 1..10 MiB. Числа свыше предела, отсутствующая длительность, неподдерживаемый MIME или иной тип **не пересылаются** ботом и не сохраняются сервером; сервер отклоняет пришедший запрос как `400 INVALID_INPUT` или `413 TOO_LARGE` без отражения полей в ошибке. Расхождение объявленного MIME с проверенным форматом при будущей обработке считается неподдерживаемым форматом. `text/plain` в будущем допускает только UTF-8; PDF допускается лишь после отдельного решения о безопасном извлечении текста. Архивы, исполняемые файлы и документы с макросами не допускаются. Эти лимиты — продуктовые пределы Vibee, а не обещание возможностей Telegram.

Для первого среза ответ media-маршрута: `{eventId, result:'accepted'|'duplicate'|'paused', revision}`. Проверки свежести (не старше 60 секунд, не более 30 секунд в будущем), привязки, неизвестного отправителя и паузы повторяют раздел B. Дедупликация общая для текста и медиа: `(bindingId,eventId)` и `(bindingId,chatId,messageId)`; один Telegram message не может учитываться дважды или превратиться в другой тип при повторе. Тот же eventId и то же каноническое тело возвращают `duplicate`; изменённое тело или другой тип для того же messageId → `409 EVENT_CONFLICT`. Ключи и keyed digest живут не более 24 часов. Если доставка неопределённа, бот повторяет тот же eventId по правилам раздела B; после исчерпания попыток ставит `transport_gap` и блокирует весь чат. Событие редактирования подписи вызывает `message_edit` и очистку открытого периода, а не переучёт.

Для будущего `chat-description` ответ имеет ту же форму. Бот создаёт стабильный eventId для одного полученного update; одинаковый `(bindingId,eventId)` с тем же телом — `duplicate`, изменённое тело — `EVENT_CONFLICT`. Новое описание заменяет старое только при актуальной revision и полном согласии. `observedAt` подчиняется тому же окну свежести. Пустое описание передаётся отдельным будущим событием очистки, а не пустой строкой этой схемы; до определения такого события его изменение не сохраняется.

На сервере первый срез хранит ограниченные метаданные и подпись максимум 15 минут после приёма; чтение всегда проверяет срок, очистка при старте и каждую минуту. После этого остаётся только техническая дедупликация до 24 часов. В будущем разрешённые временные байты файла и расшифровка удаляются не позднее 15 минут после загрузки/создания, без постоянной очереди, резервной копии, логов и передачи внешней модели по умолчанию. Отказ, отзыв, изменение состава/условий или disconnect немедленно прекращают загрузку/обработку и удаляют локальные метаданные, подписи, временные байты, расшифровки и производные данные; результат начатой операции после повторной проверки отбрасывается. Ошибка загрузки, декодирования, извлечения текста или расшифровки не подменяется пустым текстом, нулём или выдуманным результатом: временные данные удаляются, событие не включается в метрики, наружу отдаётся только технический статус без содержимого. При неопределённой доставке применяется пауза, а не молчаливый пропуск. Описание чата, когда будет реализовано, хранится максимум 15 минут, при новом описании старое удаляется; оно никогда не служит доказательством полного согласия.

Бот получает только **новые** Telegram updates после подключения; полнота истории не предполагается. Telegram может не прислать событие удаления либо не сохранить доступ к файлу до загрузки. Поэтому Vibee не обещает синхронно удалить уже полученное при удалении сообщения в Telegram и не обещает полноту медиа-периода. Если бот обнаружил правку, удаление или пропуск обновлений, который может изменить открытый период, он ставит паузу и удаляет производные данные; отсутствие сигнала удаления не трактуется как неизменность исходного сообщения. До реального включения нужно отдельно решить, допустим ли вообще вывод из медиа при такой неполноте.

Открытые решения до работы с байтами: отдельное информированное согласие на расшифровку и выбранный способ обработки (локально или проверенный провайдер), точный allowlist после проверки фактического формата, обработка PDF, политика временного хранилища и резервных копий, а также реакция на отсутствие Telegram deletion updates. Для проверки первого среза нужны синтетические HTTP/SQLite тесты полного/неполного согласия, неверного MIME и лимитов, общей дедупликации текста и медиа, TTL, отзыва и неопределённой доставки; отдельно — тесты aiogram на построение событий без вызова `getFile`. Реальные Telegram updates проверяются только после разрешённого запуска с согласованной политикой.

### Расширение Telegram v1: серверный приём расшифровок; остальное не реализовано

Расшифровка голосового активного группового чата — это **производный текст**, не исходная подпись и не второе сообщение для метрик. По образцу первого media-среза расшифровка **не входит** в `M/O/R/K` и калибровку трёх метрик, из неё не публикуются показатели и карточки. Обработка разрешена только при отдельном полном согласии на новую версию условий `synthetic-transcription-v1`: компания и **каждый** участник должны принять эту версию; `synthetic-v1` и `synthetic-media-v1` недостаточно. Переход между версиями требует сброса и повторного сбора согласий, автоматического обновления нет. Сервер независимо проверяет scoped credential, chatId, revision, полный состав и срок свидетельства согласия **до** записи. Неизвестный отправитель останавливает весь чат по существующему правилу.

| Метод /api/bot/v1/bindings/:id/... | Кто | Тело / результат |
| --- | --- | --- |
| POST .../transcription-jobs | бот | {requestId, expectedRevision, chatId, mediaMessageId, senderId, sentAt}; {jobId, status:'queued'|'accepted', revision} |
| POST .../transcriptions | бот | {requestId, expectedRevision, jobId, text, sentAt}; {jobId, result:'accepted'|'duplicate', revision} |
| GET .../transcription-jobs/:jobId | бот | {jobId, status:'queued'|'accepted'|'expired', revision} |

```ts
type TranscriptionJobRequest = {
  requestId: string        // UUID, стабилен при повторе
  expectedRevision: number // целое >= 0
  chatId: string           // отрицательный Telegram ID
  mediaMessageId: string   // положительный Telegram ID исходного голосового
  senderId: string         // положительный Telegram ID
  sentAt: string           // UTC ISO 8601 с миллисекундами и Z
}
type TranscriptionRequest = {
  requestId: string        // UUID
  expectedRevision: number // целое >= 0
  jobId: string            // UUID из шага transcription-jobs
  text: string             // непустой, до 4096 Unicode code points
  sentAt: string           // UTC ISO 8601 с миллисекундами и Z
}
```

`text` — обрезанный непустой результат расшифровки максимум 4096 Unicode code points; пустая строка запрещена. Все тела — JSON не более 32 KiB, неизвестные поля запрещены; идентификаторы и время имеют ограничения `TelegramTextEvent`. Проверки свежести `sentAt` (не старше 60 секунд, не более 30 секунд в будущем) повторяют раздел B. `expectedRevision` сверяется атомарно; расхождение — `409 STALE_REVISION`. Без полного согласия на `synthetic-transcription-v1` или при истёкшем свидетельстве — `409 CONSENT_REQUIRED`.

Дедупликация: `(bindingId, jobId)` и `(bindingId, chatId, mediaMessageId)` — keyed digest, живёт до 24 часов; один Telegram message не может породить две задачи. `requestId` идемпотентен: точный повтор возвращает прежний результат без новой записи, изменённое тело с тем же `requestId`/`jobId` — `409 EVENT_CONFLICT`. Порядок проверок: авторизация → согласия/revision → дедупликация → запись. Сырой текст расшифровки хранится максимум 15 минут после приёма (очистка при старте и каждую минуту), затем остаётся только техническая дедупликация до 24 часов. Отказ, отзыв, изменение состава/условий или `disconnect` немедленно очищают расшифровки и производные данные, как для текстов и медиа. Расшифровка не передаётся внешней модели и не входит в метрики; это не разрешение на сбор реальных голосовых — реальный маршрут остаётся выключенным до проверки источника Telegram update и согласованной политики.

### Данные, сроки и отзыв — решение для синтетического MVP

Сырые тексты: максимум 15 минут после приёма, очистка каждую минуту и при старте; чтение всегда проверяет expiresAt. Производные записи сообщения — только до закрытия периода, максимум 24 часа. Закрытые агрегаты, рекомендации, действия и отзывы чата — максимум 7 дней. Период не может быть длиннее 24 часов. Эти сроки относятся к новому чат-модулю и не меняют существующие чек-ины.

Личный Telegram-чек-ин (POST `/api/bot/v1/bindings/:id/checkins`) хранится в рабочей SQLite 30 дней от приёма: `expires = created_at + 30 дней`. Пока срок не истёк, организатор своей команды видит только агрегат по ответам; Telegram ID в таблицу не сохраняется. В момент `expires` запись перестаёт попадать в статистику, а существующая очистка (при старте и раз в минуту) удаляет её из рабочей SQLite. Это не обещает очистку резервных копий, страниц SQLite/WAL, журналов хостинга или истории Telegram: сообщения в Telegram бот не удаляет.

При отказе/отзыве, изменении состава/условий или disconnect: немедленно блокируются обработка и публикация, очищаются все тексты и производные данные привязки, включая сводки, рекомендации, чат-действия и отзывы. Ждать планового TTL нельзя. Только минимальное свидетельство версии/решения и техническая дедупликация без текста остаются до 24 часов. Disconnect удаляет связи личности. Никаких обещаний физического стирания страниц SQLite/WAL или копий Telegram.

Для реального корпоративного режима ещё нужны согласованные условия, обработчик и полномочия компании, способ подтверждения состава и политика резервных копий/удаления. До их проверки режим выключен. Внешняя модель по умолчанию выключена; синтетический demo отдельно разрешается настройкой сервера.

### Точные формулы метрик и публикация v1 (раздел A)

Профиль команды: IANA timezone; intervals — массив {day,start,end}, рабочие интервалы по ISO-дням 1..7, минуты 0..1440, [start,end), непересекающиеся; ночной интервал делится между днями. Праздники в текущем срезе не настраиваются; будущие исключения задаются явно по локальной дате. Без расписания — calibrating без чисел, в том числе при timeZone=null и intervals=[]. Версия профиля фиксируется на период; изменение отбрасывает открытый период и прежние производные данные, начинает новую калибровку. expectedVersion проверяется атомарно; workspaceId из тела не принимается.

Обозначения для одного периода: `M` — количество принятых уникальных сообщений; `N` — размер полного проверенного состава с актуальным согласием; `m_i` — количество сообщений участника `i`, включая ноль; `K` — число участников с `m_i > 0`; `O` — сообщения вне расписания; `R` — сообщения, в которых `lexicon-v1` нашёл благодарность. Повторные, невалидные, просроченные, неподтверждённые и не принятые из-за паузы события в счётчики не входят. Каждое сообщение учитывается не более одного раза.

Период пригоден для расчёта, только если он закрыт не позднее 24 часов от открытия, `K >= 5`, `M >= 20`, все авторы входят в проверенный согласившийся состав, а revision и версия профиля не менялись и пропуск транспорта не ставил чат на паузу. Иначе API возвращает `insufficient` без метрик. Для публикации дополнительно нужны три пригодных закрытых периода на трёх разных локальных датах с одинаковыми revision и версией профиля. До этого ответ — `calibrating` без чисел. После калибровки публикуются метрики последнего периода, а не среднее трёх периодов.

1. **Сообщения вне расписания (`outsideHoursPercent`).** `100 * O / M`, где сообщение относится к внерабочему, если его `sentAt`, переведённый в IANA timezone команды, попадает вне всех интервалов `[start,end)` соответствующего локального дня. Выходные и промежутки между интервалами также считаются вне расписания. Все принятые сообщения входят в знаменатель `M`; в числителе каждое учитывается максимум один раз. Это доля сообщений, а не длительность работы, нагрузка или благополучие.
2. **Равномерность участия (`participationEvenness`).** `100 * H / ln(N)`, где `H = -sum(i=1..N, p_i * ln(p_i))`, `p_i = m_i / M`; для `p_i = 0` слагаемое равно нулю. Знаменатель — полный размер состава `N`, в том числе участники с нулём сообщений; публикуется только единое командное значение. Это равномерность распределения сообщений, не оценка вклада, активности или эффективности отдельных людей.
3. **Сообщения с благодарностью (`recognitionPercent`).** `100 * R / M`. Для каждого сообщения текст приводится к Unicode lowercase и разбивается на последовательности Unicode-букв (`\p{L}+`); сообщение учитывается в `R` один раз, если есть точный токен `спасибо`, `благодарю`, `благодарим` или `thanks`. Подстрока, форма слова вне списка, сарказм и контекст не распознаются; это приблизительная частота явной лексики, не полный детектор поддержки и не показатель психологической безопасности.

Все три результата — проценты от 0 до 100, на сервере округляются до одного десятичного знака формулой `Math.round(value * 10) / 10` и передаются в JSON числами. В интерфейсе показывать знак `%`, не более одного знака после запятой; завершающий `.0` можно опустить (например, `25%`, `89.8%`, `20%`). Результаты не являются медицинской оценкой, причинным объяснением или подтверждённым улучшением.

Воспроизводимый вымышленный пример: `N=6`, `M=20`, пять авторов отправили по четыре сообщения (`m=(4,4,4,4,4,0)`), `O=5`, `R=4`. Тогда `outsideHoursPercent=25.0`, `participationEvenness=100*ln(5)/ln(6)=89.8`, `recognitionPercent=20.0`; интерфейс может показать `25% / 89.8% / 20%`.

Калибровка: минимум три допустимых закрытых периода на трёх разных локальных датах с одной версией профиля. Пока их нет — calibrating без чисел. В v1 comparison=null: нет заявлений о норме и значимости изменений. Приоритет отображения: disconnected → awaiting_consents/paused → error → open → insufficient → calibrating → published. Пропуск данных не равен нулю.

Открытый период создаётся при первом допустимом тексте после настройки расписания; periodId задаётся при закрытии. Минимальные счётчики накапливаются при приёме и переживают 15-минутный TTL сырого текста. Пропуск транспорта удаляет открытый период; отзыв или изменение состава удаляют и закрытые производные данные. Для калибровки и публикации используются только периоды текущей revision и версии профиля. Опубликованный синтетический ответ содержит demo=true. Обработчик aiogram для новых групповых текстов есть, но его работа с настоящими Telegram updates не проверялась.

### История «Пульса команды» за 7 дней

`GET /api/telegram/bindings/:id/history` — только веб-сессия организатора своей команды, только при включённом `telegramSynthetic`; иначе действуют 401/403/404 и 503 соответственно. Схема и TTL не меняются: используются сохранённые `telegram_closed_periods`, доступные 7 дней после закрытия.

Кабинет получает выбранную сервером привязку через `GET /api/telegram/summary?includeBinding=1`: `{bindingId:string|null, view:CommunicationView}`. Без параметра сохранён прежний ответ `CommunicationView`. Проверки сессии, роли и выбора привязки одинаковы; чужие bindingId браузеру не выдаются. TeamPulse использует этот ID для истории. Режим «Неделя» показывает периоды отдельно с раскрываемыми существующими графиками; пропуски и скрытые показатели не рисуются как нули или соединённые точки. «Месяц» недоступен. При смене команды/участника компонент сбрасывается; устаревшие ответы игнорируются. Известная пауза либо отказ в доступе очищают историю; серверные изменения становятся известны при следующем запросе, push-уведомлений об отзыве нет.

Ответ активного чата: `{status:'active', demo:true, window:{start,end}, revision, profileVersion, periods:[...]}`. `window` — последние 168 часов относительно серверного времени, ISO UTC; выбираются закрытия в `(start,end]`, только непросроченные строки текущей revision и версии профиля, по возрастанию времени закрытия. Открытый период в историю не входит и не скрывает закрытые периоды. Нет данных — `periods:[]`, без вымышленных нулей и заполнения пропущенных дней. Это последовательность сохранённых периодов, не дневные средние и не месячная история.

Каждый элемент содержит `period:{id,start,end}` с фактическими границами и текущий статус достаточности: `insufficient`, `calibrating` либо существующую опубликованную `CommunicationView` с тремя метриками и `comparison:null`. Метрики скрыты до той же калибровки по трём допустимым локальным датам, что используется текущей сводкой. Калибровка оценивается на момент запроса по сохранившимся периодам, поэтому истечение TTL может снова скрыть метрики. История не восстанавливает прежние ответы API.

При неактивном согласии возвращается `{status:<phase>, demo:true, window, periods:[]}`; истёкшее свидетельство даёт `paused`, отсутствие расписания — `calibrating`. Отзыв и изменение состава сохраняют существующее удаление производных данных; предыдущие revision и версии профиля не выдаются. История не сохраняет сообщения, личности, новые агрегаты или дополнительные копии данных.

### Схемы рекомендации, шага и обратной связи (раздел C)

Общие новые типы: src/core/telegram.ts, CommunicationView и CommunicationRecommendation. Старые Summary, ActionsProps, InsightsProps не меняются. Отдельные компоненты могут принимать view и recommendation; скрытые варианты CommunicationView не содержат metrics. Локальные fixtures подписываются как демо.

`CommunicationView` для опубликованного периода имеет точную форму:

```ts
type PublishedCommunicationView = {
  status: 'published'
  demo?: boolean
  period: { id: string; start: string; end: string }
  dataSource: 'chat'
  profileVersion: number
  metrics: {
    outsideHoursPercent: number
    participationEvenness: number
    recognitionPercent: number
  }
  recognitionMethod: 'lexicon-v1'
  comparison: null
}

type CommunicationRecommendation = {
  id: string
  periodId: string
  profileVersion: number
  dataSource: 'chat'
  source: 'ai' | 'template'
  observation: string
  explanation: string
  limitation: string
  action: string
  demo?: boolean
}
```

`GET telegram/bindings/:id/periods/:periodId/recommendation` доступен веб-организатору только для последнего опубликованного периода активной привязки с актуальным согласием. Четыре текстовых поля обязательны, непусты, не длиннее 500 символов каждое; неизвестные поля запрещены. Идентификатор рекомендации привязан к binding, periodId, revision и версии профиля. Провайдер получает только три опубликованных агрегата, никогда сырой текст или личности; ожидание ограничено 3 секундами и выполняется вне SQLite-транзакции. После ответа повторно проверяются сессия, права, согласия, период и версия профиля. Изменившееся состояние блокирует карточку; ошибка, timeout или неверная схема допускают возврат к шаблону только после повторной проверки. Поздний ответ игнорируется. В текущем синтетическом срезе `source='template'`, `demo=true`; внешняя модель не подключена.

`POST telegram/bindings/:id/periods/:periodId/action` принимает ровно `{requestId, expectedRevision, periodId, recommendationId, action}`: requestId и periodId — UUID, expectedRevision — целое >=0, recommendationId — 64 строчных шестнадцатеричных символа, action — обрезанный непустой текст длиной 1..500 UTF-16 code units. Только веб-организатор может подтвердить один шаг на период; periodId/recommendationId и revision должны совпасть с актуальной карточкой. Успех возвращает `{id, periodId, profileVersion, dataSource:'chat', action, confirmed:true}`. Атомарный точный повтор с тем же requestId и телом возвращает прежний ответ; изменённое тело или второй шаг для этого периода — 409 EVENT_CONFLICT. Шаг сохраняется, но автоматически не публикуется и не отправляется в Telegram; модель не имеет инструментов и не отправляет сообщения.

Обратная связь — два независимых сбора для одной опубликованной рекомендации/действия:

| Маршрут | Точное тело | Допустимые значения |
|---|---|---|
| POST .../feedback/interpretation | {requestId, expectedRevision, recommendationId, value} | useful / incorrect / usual_joke |
| POST .../feedback/outcome | {requestId, expectedRevision, actionId, value} | helped / not_helped |
| POST .../feedback/:kind/close | {requestId, expectedRevision} | Закрыть сбор; организатор |

Первые два маршрута доступны связанному веб-участнику из текущего согласившегося состава; identity и workspace определяются только по сессии, передавать их в теле нельзя. Интерпретация привязана к id карточки; outcome возможен только после подтверждения шага и привязан к его actionId. Один голос на участника и вид feedback. Успешная отправка возвращает `{accepted:true}`; точный повтор requestId и тела идемпотентен. Пока сбор открыт, изменённый запрос или второй голос возвращает 409 EVENT_CONFLICT; после закрытия новый голос отклоняется с 409 FEEDBACK_CLOSED.

`GET .../feedback/:kind` доступен организатору и до закрытия возвращает `{status:'collecting'}` без числа голосов или индивидуальных ответов. Закрытие организатором удаляет отдельные ответы и возвращает `{status:'insufficient'}` без чисел при менее чем пяти участниках либо `{status:'published', demo:true, kind, total, counts}` при пяти и более. Для interpretation counts содержит все ключи `useful`, `incorrect`, `usual_joke`; для outcome — `helped`, `not_helped`, включая нулевые значения. Повтор закрытия с исходным requestId возвращает прежний агрегированный статус; новый requestId после закрытия и новые голоса отклоняются. Отзыв согласия, изменение состава/профиля и истечение периода удаляют результаты обоих сборов. Значения индивидуальных ответов не публикуются. Старые `/actions/:id/feedback` относятся только к чек-инам.

### Личная расшифровка голосового: отдельный режим

В Python-боте добавлен opt-in `/transcribe` только для личного диалога. После отдельного одноразового согласия (5 минут) принимается одно новое непересланное `voice`: Ogg/Opus до 60 секунд и 2 МиБ. До согласия `getFile` и скачивание не вызываются. Метаданные проверяются до загрузки, фактический контейнер/кодек/длительность — в отдельном локальном процессе. Скачивание ограничено 15 секундами, распознавание — 60 секундами, результат — 2048 символами. `/stop` отзывает разрешение и отменяет работу; перед возвратом повторно проверяются разрешение и срок. Ошибка после скачивания расходует разрешение; `/transcribe` нужен заново.

Провайдер — локальный `faster-whisper` с явно установленными весами, без внешнего ИИ. Аудио и текст передаются по памяти/pipe, приложение не пишет их на диск/в БД/в журналы. Текст возвращается только в тот же личный чат без разметки. В Telegram остаются исходное сообщение и ответ; их удаление не обещается. Одновременно обрабатывается одна запись, без очереди. Весы и зависимости устанавливаются отдельно; при отсутствии настройки команда сообщает о недоступности.

Это не расширение `synthetic-media-v1`: групповые медиа-маршруты, показатели, калибровка и версии согласий не менялись. Групповая расшифровка по-прежнему выключена; отдельная версия политики, согласие компании/каждого участника и интеграция с отзывом во время ожидания ещё требуются. Срез метаданных Telegram-бота остаётся в отдельном worktree.
